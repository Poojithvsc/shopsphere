# 0013 — Secrets: AWS Parameter Store integration, designed now, gated on own-AWS

ShopSphere's two real secrets — `JWT_SECRET` and the database password — currently arrive as **environment variables** (`application.yml` resolves `${JWT_SECRET:…}` and `${DB_PASSWORD:…}`). That seam, introduced in Phase 10 and leaned on hard in Phase 11, is exactly the abstraction that lets this phase be **documentation-only**: the application already reads each secret through a placeholder and does not know or care where the value comes from. Moving the source from "an exported env var" to "an AWS-managed secret store" is therefore a change of *wiring*, not of *code*. This ADR writes down the target design so the deferral is visible and tracked, rather than living as an unrecorded gap.

**Why doc-only, why now.** Whizlabs sandbox sessions block the relevant APIs — `ssm:GetParameter` and the IAM-instance-profile machinery typically return `AccessDenied`, and you cannot scope or attach an instance role you are not permitted to create. Building the integration against a lab that rejects it would be effort spent proving nothing. The **graduation trigger is the arrival of the user's own AWS account** (per the project's cloud-scope decision: Whizlabs is for learning the reproducible IaC; persistence and account-level IAM wait for own-AWS). Until then, the env-var path stays, and this ADR is the contract for what replaces it. **XP YAGNI** — do not build against a sandbox that forbids it; capture the design and stop.

**The store: SSM Parameter Store (SecureString), not Secrets Manager — for now.** Both work. Parameter Store SecureString parameters are **free** for standard tier and KMS-encrypted at rest; Secrets Manager adds built-in rotation at ~$0.40/secret/month. ShopSphere's secrets do not rotate on a schedule yet, so Parameter Store is the cheaper, sufficient choice; the ADR flags Secrets Manager as the drop-in upgrade the day automatic rotation is wanted. **PragProg reversibility** — the two stores share Spring Cloud AWS's import mechanism, so swapping one for the other later is a property-source change, not a rewrite.

**Naming: `/shopsphere/<env>/<key>`.** Parameters live under a hierarchical prefix — `/shopsphere/prod/jwt-secret`, `/shopsphere/prod/db-password`, `/shopsphere/staging/...`. The hierarchy is what makes least-privilege IAM expressible (an instance can be granted exactly its own environment's subtree) and what lets a single `GetParametersByPath` call load every secret for a boot. **APoSD information hiding** — the path convention is the one place the "where do secrets live" knowledge sits; the app sees only the resolved property names (`jwt.secret`, `datasource.password`), never the ARNs.

**IAM: instance-profile scoped to the prefix.** The EC2 (Phase 12) carries an instance profile whose policy grants `ssm:GetParameter` / `ssm:GetParametersByPath` on `arn:aws:ssm:<region>:<acct>:parameter/shopsphere/<env>/*` **and** `kms:Decrypt` on the specific customer-managed key that encrypts those parameters — nothing wider. This is **PoEAA defence-in-depth** at the IAM boundary: a compromised instance can read its own environment's secrets and not one parameter more, and the KMS grant is what stops a leaked role from decrypting anything outside the ShopSphere key. No long-lived access keys exist anywhere in this model — the instance assumes its role, which is the whole point of moving off `terraform.tfvars` and exported variables.

**Boot-time fetch model.** Spring Cloud AWS (`spring-cloud-aws-starter-parameter-store`) resolves parameters via `spring.config.import=aws-parameterstore:/shopsphere/${ENV}/` **before** the application context refreshes, so the values are ordinary `Environment` properties by the time any bean wires. The existing placeholders do not change shape: `application.yml` still says `${JWT_SECRET}` and `${DB_PASSWORD}` — only their *source* moves from the shell to the imported property source. **PragProg DRY** — one set of placeholder names spanning localhost (env var default), Whizlabs (exported env var), and own-AWS (Parameter Store), with no `application-cloud-secrets.yml` fork to drift. That continuity is the dividend of the Phase-10 seam, paid out a third time.

A no-op `application-secrets-stub.yml` accompanies this ADR: it is **all comments**, documents the future `spring.config.import` line and the parameter names, and is bound to a profile nobody activates — so it changes no runtime behaviour and keeps `mvn verify` trivially green, while leaving the intended config in the tree where the next engineer (or future-you on own-AWS) will look for it.

Cost: zero today (no resources, no dependency added). Reversibility: total — the env-var path is untouched, so there is nothing to roll back; when own-AWS arrives, the change is adding one starter dependency and one `spring.config.import` line, exactly as this ADR specifies. The honest meta-point: the *reason* this is a clean one-line change later is that the secret was never read directly from `System.getenv` in domain code — it always came through a Spring placeholder, and **APoSD strategic programming** (build the seam before you need it) is what bought that.
