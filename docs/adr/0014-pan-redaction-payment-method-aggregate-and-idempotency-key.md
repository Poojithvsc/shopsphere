# 0014 — PAN redaction via a PaymentMethod aggregate, and Idempotency-Key on order placement

Two changes ship together because they share one theme: making order placement **safe to repeat and safe to log**. Before this phase the raw card number rode on the `OrderPlaced` event and flowed into the Payment context as a plain field; and `POST /api/v1/orders` had no dedupe, so a retried request (the browser's, the network's, or an impatient user's) created a second order. This ADR records how the card is redacted at the context boundary and how a retry is made to resolve to a single order.

## PaymentMethod as the redaction boundary

The Payment context now owns a **`PaymentMethod` aggregate** (`payment.payment_methods`, Flyway `V11`). Its only constructor is the static factory `tokenize(rawCard)`: it derives a fresh opaque `token` (a UUID), keeps just the four display digits in `last_four`, and stores a `vault_ref` that is a freshly-minted opaque handle **not derived from the PAN**. The raw card is consumed inside the factory and never assigned to a field, so it cannot leak onto an event, a log line, or any column. **DDD** — the aggregate is the consistency and naming boundary for "a tokenized instrument"; the ubiquitous-language verb is *tokenize*, and the context that owns payment data is the only one that can mint or resolve a token. A given card yields a different token on every call, which is the correct behaviour for a tokenization vault (tokens are references, not fingerprints) and incidentally means tokens carry no cross-order correlation.

The aggregate sits behind a deep module. The exposed interface `PaymentMethods` offers exactly two operations — `tokenize(rawCard) → token` and `lookup(token) → view(token, lastFour)` — and nothing else: not the entity, not the repository, not the `vault_ref`. **APoSD** — this is a deep module in the strict sense, a one-line-ish interface over the whole concern of "turn a card into something safe to pass around, and resolve it back to display data." The information hidden is substantial: the persistence mechanism, the vault-reference scheme, and above all *the card number itself*. Ordering depends only on the `tokenize` half of that interface; it holds the raw card just long enough to exchange it for a token and never sees it again. The new Ordering→Payment module edge is verified acyclic by `ApplicationModulesTests` (Payment still consumes `OrderPlaced` over Kafka with a local projection, so there is no compile cycle).

Because the simulator must still decide approve/decline/insufficient from redacted data, `PaymentSimulator` now keys on the **last four digits** rather than the full PAN (accepting either a full number or a bare last-four, which reduce to the same key). The three documented test cards remain distinguishable by their last four (`4242`/`0002`/`9995`), so behaviour is unchanged while the input is no longer sensitive. **XP YAGNI** — there is still no real vault and no encryption-at-rest beyond Postgres; the `vault_ref` is a stand-in for an external handle, and building a real crypto vault now would be effort the project's threat model does not yet justify. What matters this phase is that **no raw PAN appears in Kafka, logs, or any DB column** other than the deliberately-opaque `vault_ref` — and that property is now structurally enforced, not merely remembered.

### Migration order, in one PR, three commits

Even though ShopSphere is one deployable modulith, the event-shape change is sequenced the way a multi-service system would have to: **(1)** the Payment consumer learns to read *either* `paymentMethodToken` or the legacy `cardNumber`; **(2)** the Ordering producer flips to emitting only the token; **(3)** the consumer drops the legacy field. **PragProg** — this is the standard "expand/contract" for a shared contract, rehearsed here so the muscle exists when a future context really is deployed separately; reading the three commits in order shows a backward-compatible change at every step.

## Idempotency-Key: the database is the arbiter

`POST /api/v1/orders` accepts an optional `Idempotency-Key` header (`ordering.idempotency_keys`, Flyway `V12`, primary key `(customer_id, idempotency_key)`). The semantics: **same key + same payload → the cached order**; **same key + different payload → 422** (the key has been reused for a different request); **concurrent same-key requests → exactly one order.** The request payload is fingerprinted with a **SHA-256** of the body, so the comparison needs no stored plaintext and, critically, **no raw PAN lands in the column**.

The concurrency guarantee is delegated entirely to the **unique constraint**, not to application locking. The transactional core (`OrderPlacement`) *claims the key row before doing any work*: it inserts `(customer_id, key, request_hash, orderId)` first, so a losing concurrent caller's insert raises `DuplicateKeyException`, which rolls the whole checkout back — no order, no stock reservation, no token. The orchestrator (`CheckoutService`) then catches that exception *outside* the transaction (the boundary is split onto a separate Spring-proxied bean precisely so the rollback completes first) and reads back the winner's committed row, returning the winner's order. **PoEAA** — this is deliberately *not* a Pessimistic Offline Lock; serializing checkouts in the application would be slower and would invite deadlocks, whereas a single unique index lets the database do the arbitration it is best at. The losing transaction simply loses cleanly and reports the winner's result. **DDD** — the idempotency record is an Ordering concern (it dedupes *order placement*), so it lives in the Ordering schema next to the orders it protects, not in a shared table.

Two smaller decisions follow from the same logic. A **blank header is treated as absent**, so dedupe is strictly opt-in and the existing MVP behaviour (no header → place normally) is preserved — verified by the unchanged checkout/payment ITs. And the cached-replay path **short-circuits before touching the cart**: a second identical request returns the first order even though the cart was emptied by the first checkout, which is what makes the retry genuinely idempotent rather than an empty-cart error. **APoSD** — pulling the transactional body out of `CheckoutService` into `OrderPlacement` was the design move that made the catch-after-rollback expressible; the orchestrator reads as a short story (look up prior → place → on race, return the winner) with the messy transaction mechanics hidden one layer down.

## Consequences

No new infrastructure and no new dependency: tokenization is a UUID and a `last_four`, dedupe is one table and one SHA-256. Cost is zero. The honest limits are recorded so they are not mistaken for finished work: the `vault_ref` is a placeholder, not a real external vault; tokens are not yet reused across a customer's orders (every checkout mints a new one), which is fine for a simulator but is the obvious next deepening if a real provider is wired in Phase 15; and the idempotency table grows unbounded until a retention sweep is added. **PragProg reversibility** — both features are additive and the header is optional, so nothing here forecloses a later move to a real tokenization provider or a managed idempotency layer.
